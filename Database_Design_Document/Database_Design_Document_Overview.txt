1. Database Overall Design Principles:
	1.1 Agile Development: Initially, only core fields are retained.
	1.2 Time Consistency: UTC is the standard.
	1.3 Index Optimization
	1.4 Complete Audit Chain: All changes must be fully documented.
	1.5 Rule Tables: The rule table needs to be adapted to four basic rules first.
	1.6 Single User: No User Table

4. Detailed Table Design (Current Implementation):
	4.1 transactions
		Purpose:
			Store incoming transaction records and their processing status.
		Minimum columns required by code:
			- id BIGINT PRIMARY KEY AUTO_INCREMENT
			- account_id VARCHAR(64) NOT NULL
			- payee_id VARCHAR(64) NOT NULL
			- amount DECIMAL(18,2) NOT NULL
			- currency VARCHAR(3) NOT NULL DEFAULT 'USD'
			- trans_type VARCHAR(20) NOT NULL
			- trans_timestamp DATETIME NOT NULL
			- description TEXT NULL
			- status VARCHAR(32) NULL
			- created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
		Access patterns in code:
			- Insert transaction
			- Query by id
			- Query all
			- Count by account_id + trans_timestamp range
			- Sum(amount) by account_id + trans_timestamp range
			- Count by account_id + payee_id
			- Filter by amount range + trans_timestamp range

	4.2 monitoring_rules
		Purpose:
			Store configurable parameters and switch status for fixed monitoring rules.
		Minimum columns required by code:
			- id BIGINT PRIMARY KEY AUTO_INCREMENT
			- rule_type VARCHAR(64) NOT NULL
			- is_active TINYINT(1) NOT NULL DEFAULT 1
			- threshold_amount DECIMAL(18,2) NULL
			- max_count INT NULL
			- time_window_minutes INT NULL
			- daily_limit_amount DECIMAL(18,2) NULL
		Access patterns in code:
			- Insert rule
			- Query all rules (ORDER BY id DESC)
			- Query by id
			- Query active rules
			- Update by id
			- Delete by id

	4.3 alerts
		Purpose:
			Store alert events generated when one or more monitoring rules are triggered.
		Minimum columns required by code:
			- id BIGINT PRIMARY KEY AUTO_INCREMENT
			- transaction_id BIGINT NOT NULL
			- rule_id BIGINT NOT NULL
			- status VARCHAR(32) NOT NULL
			- severity VARCHAR(16) NOT NULL
			- created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
		Access patterns in code:
			- Insert alert
			- Query by id
			- Query all
			- Query by status
			- Update status
			- Update severity

	4.4 User_table
		Purpose:
			Store known user accounts used by payee validation logic.
		Minimum columns required by code:
			- user_name VARCHAR(128) NOT NULL
			- account_no VARCHAR(64) NOT NULL
		Access patterns in code:
			- Insert (user_name, account_no)
			- Exists check by account_no

5. Logical Relationships:
	5.1 alerts.transaction_id -> transactions.id (logical foreign key, used by service logic)
	5.2 alerts.rule_id -> monitoring_rules.id (logical foreign key, used by service logic)
	5.3 transactions.payee_id vs User_table.account_no:
		Used by rule engine to determine whether a payee is known.

	6.2 alerts.status:

7. Index Design (Recommended for Current Query Patterns):
	7.1 transactions
		- INDEX idx_tx_account_time (account_id, trans_timestamp)
		- INDEX idx_tx_account_payee (account_id, payee_id)
		- INDEX idx_tx_amount_time (amount, trans_timestamp)
	7.2 monitoring_rules
		- INDEX idx_rule_type_id (rule_type, id)
	7.3 alerts
		- INDEX idx_alert_status (status)
		- INDEX idx_alert_transaction (transaction_id)
		- INDEX idx_alert_created_at (created_at)
	7.4 User_table
		- UNIQUE INDEX uk_user_account_no (account_no)
